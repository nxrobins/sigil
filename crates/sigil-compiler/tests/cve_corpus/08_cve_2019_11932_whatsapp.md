# CVE-2019-11932: WhatsApp double-free in libpl_droidsonroids_gif

**Affected:** WhatsApp for Android before 2.19.244
**CVE record:** https://nvd.nist.gov/vuln/detail/CVE-2019-11932
**Severity:** CVSS 8.1 (High)
**Scope of claim:** CLASS

## What was the bug

WhatsApp for Android used a C library called `libpl_droidsonroids_gif` for GIF decoding. The library's `DDGifSlurp` function had a double-free bug: under certain malformed GIF inputs, a heap buffer would be freed twice.

The double-free corrupted the heap allocator's internal state. An attacker who controlled the GIF bytes (e.g., by sending a crafted GIF to a user via WhatsApp) could arrange the heap layout such that the second free triggered an arbitrary write — and from there, arbitrary code execution inside the WhatsApp process. Because WhatsApp on Android receives messages in the background and previews media automatically, the attack required no user interaction beyond the message arriving.

Disclosed October 2019. The bug was a textbook example of why memory-unsafe languages are dangerous in network-exposed parsers.

## How attackers exploited it

A crafted GIF file with malformed image-descriptor records causes `DDGifSlurp` to follow an error path that frees the same buffer twice. The attacker tunes the GIF's structure so that between the two frees, another allocation reuses the buffer's memory location, leaving the allocator's free-list pointers pointing into attacker-controlled bytes. The second free then writes those bytes back into a "free" pointer, achieving an arbitrary write.

The full exploit chain leveraged this primitive into a write-where-write-what corruption inside WhatsApp's process, then redirected control flow to attacker-controlled shellcode. Send a GIF; pop a shell.

## SIGIL's defense

The WhatsApp bug existed because C requires manual memory management and the parser logic for malformed inputs took an error path that freed a buffer twice. SIGIL has no equivalent of `free()` — values are owned by exactly one binding, and the act of "passing them somewhere else" (moving them into a send, an actor message, or another binding) IS the cleanup. There is no second cleanup to call.

The CLOSEST analog in SIGIL terms is the linear-capability use-after-move pattern. A value with linear type — like a `Frame` capability representing the parsed GIF buffer — is consumed by the first `send(Process(frame))`. Any second reference to `frame` fires O001 at compile time. The "two cleanups" pattern is rejected before the program runs.

This is not a faithful port of the C double-free (the original had no notion of linear types). It IS the closest SIGIL primitive in the same defensive role: "a value can't be used after it's been handed off."

## Vulnerable shape

See [`08_cve_2019_11932_whatsapp.sigil`](08_cve_2019_11932_whatsapp.sigil).

```sigil
on Decode(d: ActorRef<Decoder>) -> i64 {
    d.send(Process(gif_frame));
    d.send(Process(gif_frame));   // O001 — use-after-move
    return 1;
}
```

## Safe alternative

See [`08_cve_2019_11932_whatsapp_safe.sigil`](08_cve_2019_11932_whatsapp_safe.sigil). Single move; the decoder takes ownership and there is no second handoff to corrupt anything.

## Defense layer

| Original language | Defense gap | SIGIL primitive | Diagnostic |
|---|---|---|---|
| C | Manual `free()` with no compiler-tracked ownership | Linear types + move-on-pass + ownership checker | O001 |
