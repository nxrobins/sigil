# CVE-2018-1002105: Kubernetes API server privilege escalation

**Affected:** Kubernetes 1.0.x to 1.10.x; 1.11.0 to 1.11.4; 1.12.0 to 1.12.2
**CVE record:** https://nvd.nist.gov/vuln/detail/CVE-2018-1002105
**Severity:** CVSS 9.8 (Critical)
**Scope of claim:** STRUCTURAL

## What was the bug

Kubernetes' API aggregation layer proxies certain requests from the main API server to "extension" API servers (apiservers running inside the cluster as workloads). The proxy code used an HTTP connection-upgrade dance for WebSocket-style streams. The bug: when the initial upgrade handshake failed, the API server's response was an error, but the connection remained half-open. The attacker could then send subsequent (authenticated) requests over the half-open connection, which the API server forwarded to the backend extension server using its OWN high-privilege service-account credentials.

Any authenticated user with `exec` rights on any pod (a common default permission) could escalate to full cluster-admin by abusing this connection-state confusion. The bug allowed an unprivileged user to invoke privileged API operations on extension API servers — including the ability to read all secrets, run code on any node, and modify cluster-wide configuration.

## How attackers exploited it

The exploit pattern, simplified:

1. The attacker, holding only `pods/exec` rights, requests a WebSocket-style exec session.
2. The API server proxies the request to kubelet, which rejects it (the request is malformed).
3. The proxy returns an error to the attacker, but the proxied connection remains open with the API server's privileged service-account credentials still attached.
4. The attacker sends a follow-up request over the same connection — say, `GET /api/v1/namespaces/kube-system/secrets`. The proxy forwards it with the privileged credentials, returning all cluster secrets.

Mass exploitation was limited because the bug required specific configuration (extension API servers in use), but the impact on affected clusters was total cluster takeover.

## SIGIL's defense

The K8s bug fundamentally treated a USER IDENTIFIER (the original requester's identity, attached to the connection) as if it carried PRIVILEGED CREDENTIALS (the API server's service-account token). The proxy code confused the two because both were "things attached to this connection."

SIGIL refuses this kind of substitution. Every capability has a distinct TYPE. An `AdminAuth` capability is structurally distinct from a `UserId` value (an `i64`). The spawn-init type-check rejects passing an `i64` where an `AdminAuth` is required, with the T096 diagnostic ("spawn init arguments must be capability-typed").

The vulnerable fixture demonstrates this: spawning a `Worker` actor whose init signature requires `AdminAuth` with an `i64` argument fires T096. The "type confusion at the connection-state boundary" pattern is rejected at compile time.

## Vulnerable shape

See [`10_cve_2018_1002105_k8s.sigil`](10_cve_2018_1002105_k8s.sigil).

```sigil
on Start(user_id: i64) -> i64 {
    let _child = spawn::<Worker>(user_id);   // T096 — i64 where AdminAuth required
    return 1;
}
```

## Safe alternative

See [`10_cve_2018_1002105_k8s_safe.sigil`](10_cve_2018_1002105_k8s_safe.sigil). The worker receives the actual `AdminAuth` cap from state, not a user identifier.

## Defense layer

| Original language | Defense gap | SIGIL primitive | Diagnostic |
|---|---|---|---|
| Go (Kubernetes) | Connection-state-attached credentials substitutable across users | Distinct cap types + spawn-init type-check | T096 |
