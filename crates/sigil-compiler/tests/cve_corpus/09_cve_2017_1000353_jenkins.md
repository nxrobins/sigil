# CVE-2017-1000353: Jenkins Java deserialization RCE

**Affected:** Jenkins before 2.46.2, LTS before 2.46.1.1
**CVE record:** https://nvd.nist.gov/vuln/detail/CVE-2017-1000353
**Severity:** CVSS 9.8 (Critical)
**Scope of claim:** BY-CONSTRUCTION

## What was the bug

Jenkins exposed a bidirectional remoting channel for its CLI. Clients sent serialized Java objects across the channel; Jenkins called `ObjectInputStream.readObject()` on the incoming bytes. The bug: `readObject()` reifies arbitrary Java class graphs, including objects whose constructors or `readObject` methods have side effects.

Java's standard library and many popular libraries contain classes whose deserialization triggers code execution as a side effect — collectively called "gadgets." Chains of these gadgets, when reified together, achieve arbitrary code execution. The Jenkins CLI accepted ANY serialized object, including these gadget chains.

An unauthenticated attacker could send a crafted byte sequence and execute arbitrary commands as the Jenkins user — typically root or a service account with substantial privileges.

## How attackers exploited it

The canonical proof-of-concept used the `ysoserial` tool to generate gadget chain payloads — typically `CommonsCollections` or `Spring1` chains. The exploit sequence:

1. Open a TCP connection to the Jenkins CLI port (default 8080 plus CLI service).
2. Send the serialized gadget chain.
3. Jenkins calls `readObject()`, which reifies the chain, triggering its side effects: typically a `Runtime.exec()` call with attacker-controlled arguments.
4. Arbitrary shell access as the Jenkins user.

The vulnerability was found in February 2017 by independent researcher Moritz Bechler. Patches were issued April 2017; mass scanning began the same week.

## SIGIL's defense

The Jenkins bug existed because Java's standard library ships a polymorphic deserializer (`ObjectInputStream`) that REIFIES arbitrary classes from bytes, with side effects executing during reification. SIGIL has no equivalent.

Actor messages in SIGIL are statically typed. A handler `on Submit(kind: i64, job_id: i64)` knows its message has exactly that shape. The wire format is defined by the message signature; the receiver dispatches via SIGIL's typed message tag. There is no point at which bytes from the network become an executable `Runnable`. The gadget-chain class is structurally inexpressible.

This is a BY-CONSTRUCTION defense: the offending mechanism doesn't exist. No vulnerable SIGIL fixture can be written.

## Vulnerable shape

Not expressible in SIGIL. See the SIGIL defense section above for why.

## Safe alternative

See [`09_cve_2017_1000353_jenkins_safe.sigil`](09_cve_2017_1000353_jenkins_safe.sigil). Typed actor messages dispatched by tag; the receiver's handler signature pins the wire format; no polymorphic deserializer.
